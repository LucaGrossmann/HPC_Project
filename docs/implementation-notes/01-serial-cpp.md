# Part 1 — Serial C++ Baseline

Single-threaded, single-file C++ implementation of t-SVDM living in
[`HPC_Project/serial/`](../../serial/). Uses LAPACK `dgesdd` for the
per-slice SVDs and BLAS `dgemm` for the mode-3 transforms, linked via
Apple Accelerate on macOS and OpenBLAS/LAPACK on Linux. Validated by
reconstructing the input tensor and checking
`‖A − Aapprox‖_F / ‖A‖_F < 1e-10` on fixtures generated by Part 0.

## 1. Why this exists

Part 1 is the **performance baseline** for the HPC study. Every later
part (OpenMP, MPI, CUDA, Julia) reports its speedup against this
single-threaded serial time. Correctness-wise, Part 0 is the oracle,
and Part 1 must agree with it to ~1e-10 on the same seeded input.

Scope (from the plan): `tsvdm` only. t-SVDMII is deferred to when
Part 3 (MPI) needs it.

## 2. Layout convention (the #1 bug source)

Python (Part 0) uses shape `(n, m, p)` in C-order; C++ (Part 1) uses
shape `(m, p, n)` in Fortran order. They describe the *same* tensor
data but iterate differently. Frontal slice *k* is a contiguous
`m*p`-element block in both — that's the invariant both layouts
preserve, and it's what makes the fixture format simple.

```
Python  (n, m, p)  C-order        C++  (m, p, n)  column-major
┌──────────────────────────┐      ┌──────────────────────────┐
│   A[k]  is slice k        │      │  A + k*m*p  is slice k    │
│   A[k, i, j] == A_cpp(i,j,k)                                │
└──────────────────────────┘      └──────────────────────────┘
```

The fixture generator does the conversion at write time: for each
slice `k = 0..n-1` it writes `A_python[k]` in Fortran order, giving
`m*p` contiguous doubles ready for LAPACK on the C++ side. C++ just
`fread`s them.

## 3. Fixture binary format

`HPC_Project/cuda/gen_fixture.py` writes a small custom binary format:

```
offset    size              field
--------  ----------------  ---------------------------
0         4 bytes           magic = "TSVD"
4         4 bytes           int32 m
8         4 bytes           int32 p
12        4 bytes           int32 n
16        m*p*n * 8 bytes   A: n slices, each (m,p) column-major
16+mpn*8  n*n  * 8 bytes    M: (n,n) column-major
```

No dependencies on either side. The generator also prints the Python
reference's reconstruction error (~1e-15) to stdout — a sanity baseline
that the C++ side should match to floating-point noise.

separate translation units, no build graph beyond "one compile + one
link".

### `tsvdm_serial.cpp` — the five helpers

1. **`loadFixture`** — `fread` the binary format into `std::vector`s.
2. **`modeThree`** — **one** `dgemm` for the whole mode-3 product.
   See §6.
3. **`sliceSvdAll`** — loop `dgesdd` over the `n` frontal slices.
   Queries the optimal workspace once (`lwork = -1`) and reuses it.
4. **`assembleSDense`** — pack per-slice singular values (shape
   `(r, n)`) into an f-diagonal tensor (shape `(r, r, n)`) so we can
   apply the inverse mode-3 uniformly.
5. **`reconstructApprox`** — for validation only (not timed): lift
   `(U, S, V)` back to the transform domain, facewise
   `U @ S @ V^T` via two `dgemm`s per slice, then inverse mode-3.

`tsvdm(A, M, m, p, n, U, S, V)` orchestrates (1)→(4). `main` times
`tsvdm`, then runs `reconstructApprox`, prints `rel_err` and
`wall_ms`, and exits non-zero if `rel_err >= 1e-10`.

### 4.1 Where the code diverges from `plan.md`

`plan.md §4 Part 1` locks in an interface; the implementation made
three deliberate refinements while writing it. Documenting them here
so the plan and the code can be read side-by-side without surprises.
The algorithm itself and its asymptotic complexity are unchanged —
only naming, argument order, and the validation oracle moved.

| `plan.md` says | Code does | Why the code chose differently |
|---|---|---|
| `apply_M_mode3` + `apply_Minv_mode3` (two separate functions) | `modeThree(B, M, Bhat, m, p, n, bool forward)` (one function) | Forward and inverse mode-3 differ only in `dgemm`'s `transb` flag (`'T'` vs `'N'`). Folding both into one function keeps the call sites symmetric and halves the surface area to read. |
| `tsvdm(A, m, p, n, M, U, S, V)` | `tsvdm(A, M, m, p, n, U, S, V)` with `A` and `M` `const`-qualified | `A` and `M` are inputs, `(U, S, V)` are outputs. Grouping the inputs together and marking them `const` is the standard C++ convention; it also lets the compiler catch accidental writes to `A` at compile time. |
| Validation: "reconstruct in C++ and compare to the Python `tsvdm` library" (raw factor compare) | Self-reconstruction: assert `‖A − Aapprox‖_F / ‖A‖_F < 1e-10` against the input | SVD factors `(U, V)` have a column-level sign ambiguity (flip column `j` of `U` and column `j` of `V` at once and the product is unchanged). Element-wise comparison of factors fails spuriously whenever Python and LAPACK pick different signs. Reconstruction `U @ S @ V^T` is uniquely determined and bypasses the ambiguity entirely. (Already justified in §7.4.) |

The plan also lists three helpers (`apply_M_mode3`, `slice_svd_loop`,
`apply_Minv_mode3`); the code adds two more — `loadFixture` (to read
the binary fixture) and `assembleSDense` (to pack singular values
into an f-diagonal tensor) — plus `reconstructApprox` for validation.
These are bookkeeping rather than algorithmic, hence absent from the
plan's high-level pseudocode.

## 5. LAPACK / BLAS interface

Declared in one `extern "C"` block at the top of the file:

```cpp
extern "C" {
    void dgemm_ (...);
    void dgesdd_(...);
}
```

**Why Fortran-style prototypes (`dgemm_`) and not LAPACKE (`cblas_dgemm`,
`LAPACKE_dgesdd`):** Accelerate on macOS doesn't ship a usable
`lapacke.h`, but the Fortran-style symbols are in every BLAS/LAPACK
distribution. One prototype block works on Accelerate, OpenBLAS, MKL,
and BLIS without `#ifdef`s. Column-major is the native calling
convention, which matches our buffer layout directly — no transpose
flags just to cope with row-major.

**Workspace management for `dgesdd`:** query once with `lwork = -1`
and `work[0]` returns the optimal size; allocate a `std::vector<double>`
of that size; reuse it across all `n` slices. The `iwork` array is
`8 * min(m, p)` per the LAPACK reference.

## 6. One `dgemm` for the entire mode-3 product

The cute trick that makes this short. Storage `A(i, j, k) = A[i + j*m + k*m*p]`
(column-major `(m, p, n)`) is identical bytewise to an `(m*p) × n`
column-major matrix where row `r = i + j*m` and column `= k`.

The mode-3 product `Â(i, j, k) = Σ_l M(k, l) · A(i, j, l)` becomes the
2-D matmul `Â_mat = A_mat · M^T`. In BLAS:

```cpp
dgemm_('N', 'T',            // no-transpose A, transpose M
       &mp, &n, &n,
       &one, A, &mp,
       M,   &n,
       &zero, Ahat, &mp);
```

The inverse transform (apply `M^T`) is the same call with
`transb = 'N'`. Total cost of steps 1 & 3 of t-SVDM: **two `dgemm`
calls.** Not a loop of `n` small matmuls, not a custom kernel.

## 7. Design decisions

Each one, with the alternative we rejected.

### 7.1 Fortran-style prototypes over LAPACKE

See §5. Portable, no per-platform header hunt, no `#ifdef` ladders.

### 7.2 `std::vector<double>` for every buffer

**Chose:** `std::vector<double> buf(size)`, pass `buf.data()` to BLAS.
**Rejected:** raw `new double[size]` / `delete[]` pairs.
**Why:** RAII handles cleanup on every return / exception path. New
users of C++ reliably get `delete[]` wrong; `vector` makes the bug
impossible. Zero performance cost since we just use `.data()`.

### 7.3 Single-file implementation

**Chose:** everything in `tsvdm_serial.cpp`.
**Rejected:** split into `tsvdm_serial.cpp` + `tsvdm_ops.h/cpp`.
**Why:** the algorithm core is ~220 lines (the file totals 345 with
header, BLAS prototypes, and `main`). Splitting adds a Makefile rule, a
header, an include guard, and a link step — all for a one-person
project with a single TU. Part 2 (OpenMP) will copy this file and add
`#pragma omp`s; a header would need to be shared, which adds
cross-module coupling we don't need yet.

### 7.4 Validation via reconstruction, not raw factor comparison

**Chose:** compute `Aapprox = reconstruct(U, S, V, M)` and check
`‖A − Aapprox‖_F / ‖A‖_F < 1e-10`.
**Rejected:** load Python's `(U, S, V)` from a fixture and compare
element-wise.
**Why:** SVD factors have column-level sign ambiguity (every column of
`U` can flip sign if the matching column of `V` flips too). Raw
comparison would fail spuriously. Reconstruction is uniquely
determined by the input.

### 7.5 One `dgemm` for mode-3 (see §6 above)

### 7.6 Plain binary fixture over `cnpy`

**Chose:** 16-byte header + raw doubles.
**Rejected:** vendor the `cnpy` library to read `.npz` directly.
**Why:** ~30 lines of `fread` on each side vs ~500 lines of third-party
code. The on-disk format is fully documented in one comment block;
there's no hidden magic. Trade-off: fixtures are not introspectable
with `numpy.load`, but a ~5-line helper can reverse the format if
needed.

### 7.7 Factor assembly includes a slice-by-slice transpose of `V^T`

`dgesdd` returns `V^T` per slice, shape `(r, p)`. The downstream
`reconstruct` wants `V` of shape `(p, r, n)`. The transpose is
written out explicitly with two nested loops because the total work
is `O(n · r · p)` — small compared to the `dgesdd` itself — and this
is much clearer than a `dgemm`-based trick.

## 12. Reading the code: a C++ beginner's tour

This section walks through the C++ idioms in `tsvdm_serial.cpp` that
are not obvious if you came from Python. Nothing here changes what the
code does; it explains *why* the code looks the way it does. Read it
once with the source open in another window.

### 12.1 LAPACK/BLAS calling conventions (the `extern "C"` block)

`tsvdm_serial.cpp:32-49` declares the BLAS/LAPACK functions our code
will call. Three things are weird about it on first look, and all
three trace back to the same root cause: **BLAS and LAPACK are Fortran
libraries**, and we're calling Fortran from C++.

1. **Trailing underscore.** `dgemm_`, not `dgemm`. Fortran compilers
   mangle public symbol names by appending `_`. To link against the
   compiled Fortran library, our C++ declaration has to use the
   mangled name.

2. **Every argument is a pointer**, including scalars. The prototype
   has `const int* m` rather than `int m`, and the call site passes
   `&m` rather than just `m`:
   ```cpp
   dgemm_(&noTrans, &trans, &mp, &n, &n, &alpha, A, &mp, ...);
   //     ^^^^^^^                                ^^^^^
   //     pointer to a char            pointer to an int
   ```
   This is because Fortran passes everything by reference. There's no
   pass-by-value in classical Fortran; the C++ convention to interop
   is "give the address of every scalar."

3. **Single-character flags as `char` pointers.** `'N'` means "no
   transpose," `'T'` means "transpose," `'S'` (in `dgesdd`) means
   "thin SVD." These are passed as `&noTrans` (a pointer to the
   character), again because Fortran has no notion of pass-by-value.

#### Worked example: the `dgemm` call inside `modeThree`

`tsvdm_serial.cpp:110-114` applies the mode-3 transform with a single
matrix multiply:
```cpp
dgemm_(&noTrans, transb,         // (1) transpose flags for A and M
       &mp, &n, &n,              // (2) matrix dimensions
       &alpha, B, &mp,           // (3) scalar alpha, matrix A=B with leading dim mp
       M, &n,                    // (4) matrix B=M with leading dim n
       &beta, Bhat, &mp);        // (5) scalar beta, output matrix C=Bhat with leading dim mp
```
Reading the BLAS reference for `dgemm` says: `C := alpha*op(A)*op(B) + beta*C`,
where the dimensions are `op(A): m × k`, `op(B): k × n`, `C: m × n`,
and the "leading dimension" of each matrix is the stride between
successive columns in column-major storage (≥ number of rows).

So this call computes `Bhat = 1.0 · B · op(M) + 0.0 · Bhat`, where
`op(M)` is `M^T` for the forward transform and `M` for the inverse
(see §6 and §12.3 below). Dimensions: `B` is `mp × n`, `op(M)` is
`n × n`, output `Bhat` is `mp × n`.

Once you've read one BLAS call, you've read them all — they all look
like this.

### 12.2 The LAPACK workspace-query pattern

`tsvdm_serial.cpp:131-148` calls `dgesdd_` twice in sequence. The
first call is *not* doing the SVD. It's asking LAPACK how much scratch
memory to allocate:

```cpp
int lwork = -1;            // sentinel: "tell me what you need"
double workQuery = 0.0;
dgesdd_(&jobz, &m, &p, ..., &workQuery, &lwork, ...);
lwork = static_cast<int>(workQuery);   // LAPACK wrote the answer here
std::vector<double> work(lwork);       // now actually allocate
// (later) the real call uses this `work` buffer and lwork.
```

**Why LAPACK does it this way:** the optimal scratch size depends on
the algorithm chosen, the problem dimensions, and the machine
(cache sizes, vector width). Rather than hard-coding a formula,
LAPACK lets you ask the library at runtime. The `iwork` integer
buffer is sized statically by formula (`8 * min(m, p)`) because it's
small and the formula is cheap; only the floating-point `work` buffer
is queried.

We allocate once and reuse the same `work` buffer across all `n`
slices (`tsvdm_serial.cpp:148-166`). All slices have the same shape
`(m, p)`, so the optimal size is the same.

### 12.3 The mode-3 "one-`dgemm`" trick — visualized

`§6` already explains this in shorthand. Here's the long version.

**The setup.** Our tensor `A` has shape `(m, p, n)` and is stored
column-major. That means the linear index of element `A(i, j, k)` is
```
A[i + j*m + k*m*p]
```
Sliding `i` by 1 moves 1 element. Sliding `j` by 1 moves `m`
elements. Sliding `k` by 1 moves `m*p` elements.

**The observation.** Consider an `(m·p) × n` column-major matrix
`A_mat`, where row `r` of column `k` is `A_mat[r + k*(m*p)]`. If we
identify `r = i + j*m` (so `r` ranges from `0` to `m*p − 1` as
`(i, j)` ranges over `(m, p)`), then `A_mat[r + k*(m*p)] = A[i + j*m + k*m*p]`
— the same byte. **`A` viewed as a 3-D tensor and `A_mat` viewed as
a 2-D matrix sit in identical memory.** No copy, no rearrangement,
not even a different pointer.

ASCII picture:
```
3-D view: A has shape (m, p, n)         2-D view: same memory as (m*p, n)

     k=0     k=1     k=2  ...  k=n-1         column 0  column 1  ...
   ┌───────┬───────┬───────┐               ┌────────┬────────┬────
   │ slice │ slice │ slice │               │ slice  │ slice  │
   │   0   │   1   │   2   │       ===>    │   0    │   1    │ ...
   │ (m×p) │ (m×p) │ (m×p) │               │ as a   │ as a   │
   │       │       │       │               │ column │ column │
   └───────┴───────┴───────┘               └────────┴────────┴────
   Each slice is mp doubles               Each column is the same
   contiguous on disk and in              mp doubles, viewed as one
   memory.                                tall column of an (m*p)×n
                                          matrix.
```

**The math.** The mode-3 product (forward direction) is
```
Â(i, j, k) = Σ_l M(k, l) · A(i, j, l)        for l = 0..n-1
```
i.e. each tube fiber `A(i, j, :)` (length `n`) gets multiplied by `M`
on the left. With the 2-D view, fixing `i` and `j` (so `r = i + j*m`
is fixed) and reading `A_mat[r, l]` for `l = 0..n-1` is exactly the
tube fiber. So the formula above reads element-`(r, k)` of the matrix
product `A_mat · M^T`. Stacking over all `r` gives one big GEMM:
```
Â_mat = A_mat · M^T   (forward)
Â_mat = A_mat · M     (inverse, since M is orthogonal: M^{-1} = M^T)
```

That's the entire trick. Forward and inverse differ only in whether
the second operand of `dgemm` is transposed — which is exactly the
`transb` flag we toggle via the `bool forward` parameter
(`tsvdm_serial.cpp:109`).

### 12.4 Pointer arithmetic and `static_cast<size_t>`

You'll see this pattern repeatedly:
```cpp
double* aPtr = Ahat + static_cast<size_t>(k) * m * p;
```
(`tsvdm_serial.cpp:151`, similarly at `:152-154, :175-176, :205-207, :243-246`.)

The cast is defensive: it forces the multiplication to happen in
`size_t` (an unsigned 64-bit integer on this platform) rather than
`int` (a signed 32-bit integer). For small tensors it's overkill —
`k * m * p` fits in `int` for everything we test today. But for a
sufficiently large tensor (e.g. 1024³ doubles ≈ 8 GiB), the product
overflows the signed `int` range silently and you get a wraparound
to a negative or absurd offset, then a segfault or — worse — silent
memory corruption.

Casting one operand to `size_t` makes C++'s usual-arithmetic-conversion
rules promote the whole multiplication to `size_t`. The cost is one
verbose-looking line of code in exchange for never having to think
about `int` overflow on big inputs.

### 12.5 The `V^T → V` transpose loop

`dgesdd` returns `V^T` per slice, packed as a contiguous `(r × p)`
column-major matrix. The downstream `reconstruct` wants `V` per slice,
shape `(p × r)` column-major. So we transpose, slice by slice, with
two nested loops (`tsvdm_serial.cpp:205-214`):
```cpp
for (int k = 0; k < n; ++k) {
    const double* src = VtHat.data() + static_cast<size_t>(k) * r * p;
    double* dst       = Vhat.data()  + static_cast<size_t>(k) * p * r;
    for (int i = 0; i < r; ++i) {
        for (int j = 0; j < p; ++j) {
            // VtHat(i, j, k)  ->  Vhat(j, i, k)
            dst[j + i * p] = src[i + j * r];
        }
    }
}
```
Reading the index expressions:
- `src[i + j * r]` — `i` is the row, `j` is the column, leading dim
  `r`. This is the `(r × p)` `V^T` slice.
- `dst[j + i * p]` — `j` is the row, `i` is the column, leading dim
  `p`. This is the `(p × r)` `V` slice. We've swapped the role of
  `i` and `j`, which is what "transpose" means in column-major
  notation.

§7.7 explains why we don't use a `dgemm`-based transpose trick: the
total work `O(n·r·p)` is dwarfed by `dgesdd`, so explicit clarity wins.

### 12.6 The f-diagonal packing in `assembleSDense`

`tsvdm_serial.cpp:170-179`:
```cpp
std::fill(Shat, Shat + static_cast<size_t>(r) * r * n, 0.0);
for (int k = 0; k < n; ++k) {
    for (int i = 0; i < r; ++i) {
        // Shat(i, i, k) = s(i, k)
        Shat[i + i * r + k * r * r] = sHat[i + k * r];
    }
}
```
We're constructing an "f-diagonal" tensor: a 3-D tensor of shape
`(r, r, n)` where each frontal slice is a diagonal `r × r` matrix.
The non-zero entries are `Shat(i, i, k) = s(i, k)`; everything else
is zero (hence the `std::fill` first).

The index `i + i * r + k * r * r` is the column-major linearization
of position `(i, i, k)` in shape `(r, r, n)`:
```
linear_index(row, col, slice) = row + col * r + slice * r * r
                              = i  + i  *  r + k     *  r * r
```
because we want row `i` and column `i` (the diagonal), within slice
`k`. The arithmetic looks busy but it's just the same `(i, j, k) →
flat` formula from §2 with the row-and-column indices both equal
to `i`.

### 12.7 Why `reconstructApprox` re-applies the forward mode-3

A common reading-comprehension pothole. `tsvdm` ends by inverse-
transforming `(Û, Ŝ, V̂) → (U, S, V)`, leaving the factors in the
**spatial** domain. `reconstructApprox` then does this
(`tsvdm_serial.cpp:227-233`):
```cpp
modeThree(U, M, Uhat.data(), m, r, n, /*forward=*/true);
modeThree(S, M, Shat.data(), r, r, n, /*forward=*/true);
modeThree(V, M, Vhat.data(), p, r, n, /*forward=*/true);
```
Forward — sending `(U, S, V)` *back* to the transform domain. Why?

Because the M-product is **defined** as: lift to transform domain →
multiply slice-by-slice → bring back. There is no shortcut for
`U ⋆_M S ⋆_M V^T` in the spatial domain. So to compute
`Aapprox = U ⋆_M S ⋆_M V^T`, we have to:
1. Forward-transform `(U, S, V)` (re-entering transform domain),
2. Do the facewise matmul `Û · Ŝ · V̂^T` slice by slice
   (`tsvdm_serial.cpp:242-256`),
3. Inverse-transform the product back to the spatial domain.

Yes, this means the forward transform is applied twice in `main`
(once at the start of `tsvdm`, once at the start of `reconstructApprox`),
and the inverse twice as well. §10 calls this redundancy deliberate;
the reason is that we want `tsvdm`'s timing to be independent of
the validation path. If we kept `(U, S, V)` in transform domain to
avoid the round-trip, callers would have to know which domain the
factors live in, and we'd have to re-document that contract every
time `tsvdm` is called.

### 12.8 Mixed C-style I/O inside modern C++

`loadFixture` (`tsvdm_serial.cpp:62-93`) uses `std::fopen` /
`std::fread` / `std::fclose` rather than the C++-stylish
`std::ifstream`. Why the C-style API in an otherwise modern-C++
file?

The fixture format is "16-byte header + raw doubles." `fread` reads
exactly N bytes into a buffer in one call, which matches the binary-
blob shape of the format. `std::ifstream` in binary mode does the
same job, but with more ceremony (`reinterpret_cast<char*>`, manual
state checking via `is.gcount()`, and so on). Neither is wrong; the
file picks the lower-overhead option.

The rest of the file (`std::vector` for buffers, `std::chrono` for
timing, `std::min`, `std::sort`) is idiomatic C++17.
